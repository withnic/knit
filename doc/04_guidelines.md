04. 開発ガイドライン・規約 (Development Guidelines)
本ドキュメントは、knit プロジェクトにおけるコード設計基準、テスト実行戦略、品質保証原則および禁止事項を定義します。開発に関わるすべてのメンバーは、以下の要件に準拠してコードの実装を行ってください。
1. Goコーディング規約と設計原則
プロジェクトの保全性と拡張性を高めるため、以下の設計原則を徹底します。
標準ライブラリ優先ポリシー
依存ライブラリの肥大化（Dependency Bloat）を防止し、ビルド性能と安全性を確保するため、パッケージごとに利用可能なライブラリを制限します。

tia パッケージ
AST（抽象構文木）解析および周辺処理においては、サードパーティ製ライブラリへの外部依存を一切排除します。
Goの標準ライブラリ（go/parser, go/ast, go/token, go/format）のみを最大限活用して実装してください。
di パッケージ
高度な型解決およびクロスパッケージのシンボル解析が必要となる部分に限り、準標準ライブラリである golang.org/x/tools/go/packages の利用を許可します。
決定論的出力の保証 (Deterministic Output)
同一の入力ソースコードに対しては、常にバイトレベルで一致するコード生成物およびテスト出力を生成しなければなりません。

Go言語の map イテレーション順序は非決定論的であるため、map の走査結果をそのままコード生成やテストリスト出力に利用することを厳禁とします。
すべてのスライス、変数宣言、import ステートメント、および -run 正規表現パターンは、出力バッファへ書き込む直前に必ず sort.Strings 等を用いて一意にソート処理を実行してください。
明確なエラーハンドリングとトレーサビリティ
DI（依存性注入）の解決フェーズでエラーが発生した際、デバッグの手間を最小限に抑えるため、詳細なコンテキスト情報を含めたエラーメッセージを出力します。

対象となるエラー状況: プロバイダ不足（Missing Provider）、重複プロバイダ（Duplicate Provider）、循環依存（Circular Dependency）
必須情報: 「どのInjectorの処理中か」「どの型を解決しようとして失敗したか」を示す完全な依存チェーン（Dependency Chain）情報をエラー文に組み込んでください。

[Error Example]
failed to resolve provider for injector 'InitializeUserService':
  UserService -> UserRepository -> *db.Pool (provider not found)


2. テスト戦略（ドッグフーディング）
本プロジェクト自体も提案モデルに倣い、Fast Feedbackを実現するためにSmall（ユニット）テストとMedium（結合）テストを厳格に分離する設計を採用します。

テスト分類
実行スコープ / コマンド
目標実行時間
目的と検証内容
Small（ユニット）
go test -short ./...
1秒以内（全件）
高速なフィードバック。AST解析・コード生成ロジックの単体検証。
Medium（結合）
go test ./...
5〜10秒以内
実際のファイルシステムやGit状態変更を伴うE2E（End-to-End）動作検証。

ユニットテスト（Small Test）のガイドライン
高速性の維持: go test -short ./... で全件実行した際、完了まで1秒を超えてはなりません。
テスト構造: 原則としてテーブル駆動テスト（Table-Driven Tests）形式で記述します。
フィクスチャ管理: AST解析やコード生成のテストには、インメモリ文字列または testdata/ ディレクトリ配下に置かれた最小限のサンプルGoコードフィクスチャを使用してください。
コンパイル可能性検証: 生成された wire_gen.go 相当のコードが構文的に正しいだけでなく、実際にコンパイルおよび実行可能であることを go/types パッケージによる型チェック、またはサブプロセス経由の go test で検証するテストケースを必ず含めてください。
結合テスト（Medium Test）のガイドライン
アイソレーション: t.TempDir() を利用して一時的なGitリポジトリ環境を動的に構築します。
シナリオ検証: 一時リポジトリ内で git commit やファイルの変更処理を行い、knit tia コマンドが変更差分を正確に認識し、期待される結合テストのみを抽出・実行するかを検証するE2Eテストを実装してください。


3. 安全側へのフォールバック原則（TIA）
Test Impact Analysis（TIA）において、テストの実行漏れ（False Negative）は潜在的なバグの見逃しに直結するため、最も回避すべきリスクです。解析不可能なケースや動的な挙動が含まれる場合は、常に**「安全側（テストを実行する側）」**に倒して処理します。

インターフェース呼び出しの解釈
静的な型解析のみで呼び出し先を特定しきれないインターフェース経由のメソッド呼び出しについては、プロジェクト内で同一のメソッド署名（Signature）を持つすべての実装クラス・呼び出し元をテスト候補に含めます。
非Goファイル変更時の動作
.sql などのデータベース関連ファイルやマイグレーションファイルの変更検知時は、影響範囲を過小評価せず、リポジトリ層（Repository Layer）の結合テストを自動的に実行対象へ組み込める拡張性を保持してください。


4. 禁止事項 (Prohibitions)
プロジェクトの保守性とスコープ管理を徹底するため、以下の行為を厳重に禁止します。

スコープクリープの防止
プロダクトオーナーの合意なしに、wire.Struct や wire.Value といった複雑な構文のサポートを独断でコードベースに追加することを禁止します。初期フェーズでは最小限の仕様に焦点を当てます。
生成ヘッダーの自動付与義務
本ツールが自動生成するすべてのコードファイル（wire_gen.go 等）の先頭には、手動編集を防止するための標準ヘッダーコメントを必ず付与してください。
ヘッダー文字列: // Code generated by knit. DO NOT EDIT.


5. 開発仕様チェックリスト
プルリクエスト（PR）を提出する前に、以下の項目を満たしているか確認してください。

go test -short ./... が1秒以内にエラーなく完了する
コード生成結果がソートされており、何度実行しても差分が発生しない（決定論的出力）
新規プロバイダ・構文の解析失敗時に依存チェーンを含んだエラーメッセージが返される
自動生成されるコードの先頭に // Code generated by knit. DO NOT EDIT. が含まれている
外部依存関係が本ガイドラインの規定（tia パッケージは標準ライブラリのみ）に従っている


6. テストマトリクス（Test Matrix）
実装完了の条件として、以下のエッジケースを検証するユニットテスト / 結合テストを必ず網羅すること。

knit gen 側の必須テストケース
wire.go に //go:build wireinject が付与されていても正しくロード・解析できること。
プロバイダが (T, func(), error) を返し、途中でエラーになった場合にクリーンアップ関数が LIFO（後入れ先出し）で呼ばれるコードが生成されること。
同一構造体名だが別パッケージ（pkgA.Config, pkgB.Config）の依存が衝突せずに解決・変数採番されること。
可変長引数（...Option）を使用する関数を検知した場合、パニックさせずに分かりやすいエラーで停止すること。
knit tia 側の必須テストケース
*_test.go 自体を変更した場合、ハブやDIグラフに依存せず、そのテストが即座に実行対象として抽出されること。
SQLファイル（.sql）変更時、同階層にあるGoパッケージがシードとして認識され、DB層のテストへ波及すること。
偽陽性テスト: 同名メソッド（Create）が別パッケージに存在する場合、対象ファイルを import していない呼び出し元のテストが誤って実行されないこと。


7. 実装フェーズ分割（Claude Code 実装ステップ）
Phase 1: DIコア解析 (internal/di/loader.go, resolver.go): packages.Load（-tags=wireinject対応）、TypeKey 完全修飾化、トポロジカルソート。循環参照・プロバイダ不足時に依存チェーンを含むエラーを返すこと。
Phase 2: DIコード生成 (internal/di/generator.go, graph_export.go): LIFOクリーンアップ展開、決定論的変数採番、go/format 整形、.knit/di-graph.json 出力。生成コードがソートされコンパイルが通ること。
Phase 3: TIA 軽量パース (internal/tia/diff.go, scanner.go): git diff 抽出と go/parser 並列走査、ImportMap 構築。変更箇所から SymbolNode シードリストを1秒以内に抽出できること。
Phase 4: TIA 逆引きと実行 (internal/tia/analyzer.go, runner.go): 逆引きBFS、ハブ停止、di-graph.json とのサブグラフ交差判定、go test コマンド組み立て。一時リポジトリでのE2Eで対象結合テストのみが選別・実行されること。
