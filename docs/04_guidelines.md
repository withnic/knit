# 04. 開発ガイドライン・規約 (Development Guidelines)

本ドキュメントは、knit におけるコード設計基準、テスト戦略、品質保証の原則と禁止事項を定義します。

## 1. Go コーディング規約と設計原則

### 依存ライブラリの制限

依存ライブラリの肥大化（Dependency Bloat）を防ぎ、ビルド性能と安全性を確保するため、外部依存は高度な型解決とクロスパッケージのシンボル解析に必要な準標準ライブラリ **`golang.org/x/tools/go/packages` のみ** とします。それ以外は標準ライブラリで実装してください。この制限は golangci-lint の depguard で検査されます。

### 決定論的出力の保証 (Deterministic Output)

同一の入力ソースコードに対しては、常にバイト単位で一致するコードと依存グラフを生成しなければなりません。

- map の走査結果をそのままコード生成やグラフ出力に使うことを禁止します。
- スライス、変数宣言、import、Injector・依存の一覧は、出力する前に必ずソートしてください。

### 明確なエラーハンドリングとトレーサビリティ

依存解決でエラーが発生した場合、デバッグの手間を最小限にするため、詳細なコンテキストを含めたエラーメッセージを出力します。

- 対象: プロバイダ不足（Missing Provider）、重複プロバイダ（Duplicate Provider）、循環依存（Circular Dependency）、クリーンアップ・error を返せない Injector
- 必須情報: 「どの Injector の処理中か」と、ルート型から失敗した型までの完全な依存チェーン

```
failed to resolve provider for injector 'InitializeUserService':
  service.UserService -> repo.UserRepository -> *db.Pool (provider not found)
```

- 複数の Injector・パッケージにエラーがある場合は、1 回の実行でまとめて報告します。
- 対象外の構文や不正なシグネチャは、ソース位置と代替手段を含めたエラーにします（パニックさせない）。

## 2. テスト戦略

Fast Feedback を実現するため、Small（ユニット）テストと Medium（E2E）テストを分離します。

| 分類 | コマンド | 目標実行時間 | 内容 |
|---|---|---|---|
| Small | `make test`（`go test -short ./...`） | 全件 1 秒以内 | 解析・解決・コード生成ロジックの検証 |
| Medium | `make test-all`（`go test ./...`） | 5〜10 秒以内 | 一時ディレクトリでの生成・ビルド・実行を伴う E2E 検証 |

### Small テストのガイドライン

- **高速性の維持**: `go test -short ./...` の全件が 1 秒を超えてはならない。`packages.Load` はテストバイナリごとに 1 回にまとめ、追加のロードが必要なテストは `testing.Short()` でスキップする。
- **テスト構造**: 原則としてテーブル駆動テストで書く。
- **フィクスチャ**: 主なフィクスチャは wire モードの `internal/di/testdata/fixture`（独立モジュール `example.com/fixture`、google/wire のスタブ `internal/di/testdata/wire`）。knit モードは `internal/di/testdata/knitfixture` を使い、マーカーパッケージのスタブはリポジトリ直下の実物の `knit.go` からテスト時に一時ディレクトリへ組み立てる（実 API とずれないように）。テストは `GOWORK=off GOFLAGS=-mod=mod GOPROXY=off` でネットワークなしに実行する。
- **ゴールデンファイル**: 生成コードは `internal/di/testdata/golden/*.golden` と比較する。意図した変更は `go test ./internal/di -run TestGenerateFile_Golden -update` で更新し、差分をレビューする。
- **コンパイル可能性の検証**: 生成コードは、パッケージの Injector 宣言以外のファイル（タグなしで build されるファイル）と合わせて `go/types` で型チェックする。

### Medium テストのガイドライン

- **アイソレーション**: `t.TempDir()` にフィクスチャをコピーし、元の `testdata` を書き換えない。
- **シナリオ検証**: 実際に `knit gen` 相当の処理でファイルを書き込み、`go build` / `go vet` / `go test` で生成コードが動作すること（LIFO クリーンアップを含む）を確認する。

## 3. 禁止事項 (Prohibitions)

- **スコープクリープの防止**: プロダクトオーナーの合意なしに、`wire.Struct`、`wire.Value`、`wire.InterfaceValue`、`wire.FieldsOf` などのサポートを追加しない。
- **生成ヘッダーの省略禁止**: 自動生成するすべてのファイルの先頭に `// Code generated by knit. DO NOT EDIT.` を付ける。
- **依存グラフの互換性**: `di-graph.json` のフィールドを削除・意味変更する場合は `version` を上げる。

## 4. 開発チェックリスト

変更を提出する前に、以下を満たしていることを確認してください。

- `make check`（go.mod の tidy、フォーマット、リント、ユニットテスト）がパスする
- `make test-all` がパスする
- `go test -short ./...` が 1 秒以内に完了する
- 生成結果がソートされており、何度実行しても差分が出ない
- 解決エラーに Injector 名と依存チェーンが含まれる
- 生成コードの先頭に `// Code generated by knit. DO NOT EDIT.` が含まれる
- 外部依存が `golang.org/x/tools/go/packages` のみである

## 5. テストマトリクス (Test Matrix)

以下のエッジケースをテストで網羅すること。

| 観点 | 期待する動作 |
|---|---|
| ビルドタグ | `//go:build wireinject` 付きの `wire.go` を正しくロード・解析し、古い `wire_gen.go`（`!wireinject`）は無視する |
| モード | デフォルトの knit モードで `knit.Build` / `knit.NewSet` / `knit.Bind` を解析し、`!knitinject` 付きの `knit_gen.go` を生成・実行できる。`-mode=wire` で wire と同じ入出力になる。各モードはもう一方の宣言を拾わず、もう一方のモードを示すエラーを返す |
| LIFO クリーンアップ | `(T, func(), error)` のプロバイダが途中で失敗した場合、成功済みのクリーンアップが逆順に呼ばれる（実行して確認） |
| 同名型 | 別パッケージの同名型（`pkga.Config`、`pkgb.Config`）が衝突せずに解決・採番される |
| 名前衝突 | 同名パッケージ、`v1` という名前のパッケージ、引数名・パッケージレベルの識別子と衝突しない import 名・変数名が付く |
| 可変長引数 | `...Option` を持つ関数を検出したら、パニックせずに分かりやすいエラーで停止する |
| 対象外構文 | `wire.Value` などを検出したら、代替手段を示すエラーで停止する |
| 解決エラー | 循環参照・プロバイダ不足で依存チェーン付きのエラーを返す |
| 決定論 | 入力順を変えても生成コードがバイト単位で一致する |
| 依存グラフ | Bind エントリに `bound_from` が付き、Injector・依存がソートされている |
